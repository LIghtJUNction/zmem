# 0.1.1 控制值与升级验收

验收日期：2026-11-22（Asia/Taipei）。宿主机为 Linux 7.3.5-arch1-1、systemd、cgroup v2，基页大小 4096 字节。验证使用本版修复源码；发布工作流随后只递增版本字段。

## 发现的问题

完整套件在后台编译时，0.1.0 报告了 memory.high 的外部修改，但实际差异来自内核把字节限额向下取整到完整页。旧日志保存了请求值，后续采样读到取整后的值，两者不相等，控制器因此停止继续调整该限额。

| 控制项 | 请求字节数 | 内核实际字节数 |
| --- | ---: | ---: |
| 后台 memory.high | 11533690420 | 11533688832 |
| 会话 memory.low | 1544690688 | 1544687616 |
| 应用 memory.low | 514896896 | 514895872 |

这个差异不能通过放宽所有比较来解决：另一个管理器或用户确实修改限额时，zmem 仍应保留对方的设置。

## 修复

内存控制值按运行内核报告的页大小统一规范化；实际写入值、内存中的记录和持久日志一致。五列旧日志的恢复也使用同样的规范。新日志增加一个可选字段，区分尚未完成的写入与已确认写入，覆盖写入前后退出的恢复窗口。设备号和 inode 仍用于避免把旧记录应用到同名新 cgroup。

0.1.0 的退出路径可能删除未正确恢复的旧日志。升级器会先持久保存恢复记录，对五列格式使用本次调用专属的临时 systemd 停止设置，停止旧管理器后读取最终日志，再执行新恢复逻辑。只有恢复与核对均成功后才删除记录。六列格式继续正常停止。临时设置不覆盖用户已有文件，并在停止操作后清理；无法确认的旧控制值保留证据并返回错误。

## 验收结果

| 检查 | 结果 |
| --- | --- |
| 常规 Rust 测试 | 31 项通过 |
| 严格 lint | Clippy all-targets，warnings 视为错误，通过 |
| 核心可移植性 | no_std 核心检查通过 |
| 真实内核回归 | 1 项特权测试通过 |
| 旧版升级 | 从正在运行的 0.1.0 控制器成功接管 |
| 旧日志基线 | 原有 13 项控制值在停止后均恢复到记录的原值 |
| 配置 | 升级前后 SHA-256 一致 |
| Swap | 升级前全部活动设备/文件继续活动 |
| 服务 | 升级及回归后恢复 active；采样无诊断错误 |
| 临时文件 | 本次 runtime drop-in、恢复日志和空测试 cgroup 均清理 |

真实内核测试只创建一个没有进程的独立 cgroup，连续写入两个未按页对齐的 high/low 值，检查实际值与日志一致，再检查恢复。它还验证了外部修改不被覆盖，以及五列旧记录能够恢复。测试没有制造整机内存耗尽。

原始日志和现场 JSON 留在开发工作区的 ignored artifacts 目录；Git 只保存文字记录与测试源码。常规测试默认跳过此特权用例。维护者应先完成正在运行的 daemon 的控制恢复，再执行该测试，不能与真实控制器并发运行。

## 证据边界

这次验证确认了控制值规范化、连续调整、外部设置保护和旧版升级路径。此前的后台软限额、可丢弃任务硬限额、Btrfs Swap 扩容和完整回滚记录见 [0.1.0 宿主机验收](acceptance-0.1.0.md)。

本次没有重启正在使用的宿主机，也没有完成多日稳定性实验。当前证据不能推导出所有负载下不会卡顿、不会发生 OOM，或任意程序都能保存未提交数据。
