01 / 控制回路

先看压力，再分配余量。

内存用得多很正常。zmem 更关心任务是否正在等待内存，以及下一步动作会带来多少代价。

01

观察实际阻塞

分别报告内存压力与 IO 拥塞。结合可用内存、PSI 等待时间、文件页回收后的再次访问与交换活动，判断下一步动作的代价。

observe
02

小步调节，保留任务

按观测到的换页代价调节交换偏好，为纳管后台设置预算。沿实际 cgroup 层级保护识别出的桌面、终端与远程连接。

adapt
03

稳定后逐步恢复

无进展的回收进入退避，遗留 Swap 文件逐个检查。活动 Swap 缩容等待持续恢复，并预留整文件迁移余量；去重扫描也等待稳定后恢复。

03 / 明确的职责

把管理能力收在一个地方。

管理交换空间的生命周期

按配置批量扩容，逐个清理遗留的自有文件。活动 Swap 缩容须通过持续健康与整文件余量检查；内核保护仍在使用的文件。

zram / swap lifecycle

先检查余量，再启动后台

用 zmem run 提交任务。内存紧张时先等待，恢复稳定后错开放行；运行后共享后台预算。默认等待 60 秒，超时不启动命令。

cgroup v2 / memory.high

每一步都能解释

status 保留守护程序状态，按需补充当前进程列表。--live 与 plan 明确显示独立、未应用的预览，JSON 同时提供来源与覆盖范围。

status / plan / schema

为明确注册的任务去重

用 --dedup 注册可信的后台或可丢弃任务。CPU、内存或 IO 繁忙时暂停扫描，保留已合并的页；KSM 匹配域跨进程与用户。

KSM / explicit registration

维护尝试至少间隔 60 秒，一次最多一个文件；活动缩容默认等待连续健康 600 秒。去重扫描等待稳定 30 秒后恢复，采用 128 页批次与 100 ms 休眠，不代表硬性 CPU 配额。

内核负责分页、页面合并与最终 OOM。zmem 不自动注册全部应用，不强制拆散已合并页，也不对活动 Swap 做文件系统去重。应用检查点、计算进度恢复与能耗优化仍是后续方向。

04 / 开始使用

先读状态，再让 zmem 接管。

适用于支持 PSI、cgroup v2 与 systemd 的 Linux。安装管理服务需要 root 权限。

从 crates.io 安装
cargo install zmem-manager --locked
zmem doctor
zmem status --json
sudo "$(command -v zmem)" install --replace

下载 Linux x86_64 / ARM64 预编译包 ↗

原位接管，保留恢复入口。

安装器保存服务与配置，并保留活动 Swap。安装失败恢复本次操作前的状态；显式 rollback 使用首次安装基线。升级或停止 zmem 不主动排空交换区。

sudo zmem rollback恢复首次安装的管理基线

完整安装与恢复说明↗
命令用途
zmem status --json --processes读取守护程序报告并补充当前进程
zmem status --live --json独立取样预览，速率尚未预热
zmem plan --json查看独立策略预览，不执行动作
zmem daemon --observe持续观察并输出未应用的决策
zmem run --class background -- cargo build等待内存余量，再运行后台构建
zmem run --class background --dedup -- YOUR_TRUSTED_COMMAND为可信任务注册内存去重
zmem schema读取面向 AI 的命令契约

报告区分计划与实际控制值，保留最近一次前台保护检查的时间与错误。去重任务每 10 秒有界扫描一次，报告覆盖、KSM 状态与系统级收益估计；缺失指标保留 null。无守护程序报告时明确返回独立快照。

源码中的 measure_responsiveness.py 可记录自然负载下的调度延迟、PSI、换页和后台活动。可选桌面探针测量进程与 IPC 往返时间。前后观测用于比较同类工作窗口，因果判断需要控制工作负载与缓存条件。

验收记录分别标明版本、测试环境与观测窗口。启动准入只覆盖显式提交的任务；当前机制不承诺内存节省量、桌面延迟或彻底消除卡顿。
